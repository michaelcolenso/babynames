# SEO Audit — nobodynamed.com

**Date:** 2026-05-29
**Scope:** Full technical + on-page SEO audit of the live production site and the code that generates it (`apps/web`, `packages/shared`).
**Method:** Live HTTP inspection (headers, rendered HTML, content negotiation, redirects, status codes, structured data) cross-referenced against the source in this repo. Ahrefs/GSC live ranking data was unavailable on the connected plan, so off-page metrics (backlinks, keyword rankings, traffic) are out of scope for this pass — see [§7](#7-what-this-audit-could-not-cover).

---

## Executive summary

NobodyNamed is, on the whole, a **well-engineered site for SEO**. Server-side rendering, clean canonical/redirect handling, rich per-page metadata, dynamic OG images, JSON-LD on every template, a curated XML sitemap, and excellent edge performance (TTFB ~70 ms) are all in place. The programmatic-SEO surface (name, year, decade, letter, and editorial hub pages) is thoughtfully built.

There is, however, **one critical regression that undermines the most important page on the site**, plus a handful of smaller fixes and growth opportunities.

| # | Severity | Issue | Effort |
|---|----------|-------|--------|
| 1 | 🔴 **P0 — Critical** | Homepage `/` serves raw **`text/markdown`** to all clients (browsers + Googlebot), not HTML | Low |
| 2 | 🟠 P1 | Homepage HTML asset (`/index.html`) — with its `WebSite`/`SearchAction` schema and internal links — is never delivered | Low (same fix as #1) |
| 3 | 🟡 P2 | Homepage `og:image:type` declares `image/svg+xml` but the endpoint returns `image/png` | Trivial |
| 4 | 🟡 P2 | XML sitemap has no `<lastmod>`; covers ~2k of ~100k name pages | Low–Med |
| 5 | 🟢 P3 | OG images lack declared `width`/`height`; no sitewide `Organization` schema | Low |
| 6 | 🟢 P3 | Growth: expand indexable name coverage + sitemap index | Med |

Everything in §3 ("What's already excellent") is working and should be preserved.

## 1. 🔴 P0 — The homepage serves Markdown instead of HTML

### Evidence
Every request to `https://nobodynamed.com/` — regardless of `Accept` header, User-Agent, or `Sec-Fetch-*` headers — returns the Markdown API document, not the HTML homepage:

```
$ curl -s -A 'Mozilla/5.0 ... Chrome/120 Safari/537.36' \
       -H 'Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8' \
       -H 'Sec-Fetch-Dest: document' -H 'Sec-Fetch-Mode: navigate' \
       -D - -o body.txt https://nobodynamed.com/

content-type: text/markdown; charset=utf-8
x-markdown-tokens: 547

$ head -1 body.txt
# NobodyNamed
```

Confirmed with: default `curl` (`*/*`), `Accept: text/html` only, full Chrome `Accept` + `Sec-Fetch` headers, Googlebot UA, and the WebFetch tool. **All receive Markdown.** `cf-cache-status: DYNAMIC` rules out a poisoned cache entry. The served body contains **zero `<a>` links, no `<title>`, no meta description, no canonical, no Open Graph tags, and no JSON-LD.**

The intended behavior (and the *correct* logic currently in the repo at `apps/web/functions/index.ts`) is to serve Markdown **only** when the client explicitly asks for it:

```ts
if (accept.includes("text/markdown")) { /* serve markdown */ }
// otherwise fall through to ASSETS.fetch() → HTML
```

The deployed handler is returning Markdown unconditionally — i.e. the live code is out of sync with (or a regressed version of) the source in this branch.

### Why this is critical
The root URL is almost always a site's highest-authority page and the primary entry point for brand/navigational queries. Right now Google indexes a 547-token plain-text document with:

- **No `<title>` or meta description** → Google must synthesize a snippet from raw Markdown; the carefully written "NobodyNamed — A cultural history of American names" title never reaches the SERP.
- **No internal links** → the root passes **no link equity** to `/extinct`, `/rising`, `/year`, name pages, blog, or viz. Crawl discovery and PageRank flow from the homepage are effectively zeroed.
- **No `WebSite` + `SearchAction` schema** → forfeits the Google Sitelinks Search Box eligibility that `public/index.html` was built to earn.
- **Human visitors** navigating in a browser are served plain text rendered as an unstyled page (or a download prompt) — a direct UX/bounce-rate problem that also feeds negative engagement signals.

### Fix
1. **Verify** in a real browser that the live homepage renders as plain text (reproduce the curl result above).
2. **Deploy the current `apps/web/functions/index.ts`** from this repo (its `Accept` check is correct), or correct the deployed handler so Markdown is gated behind an explicit `Accept: text/markdown` (and/or a `?format=md` query param). Browsers and search crawlers must get the HTML asset.
3. After deploy, re-validate: `curl -s -H 'Accept: text/html' https://nobodynamed.com/ | head -1` should return `<!doctype html>`.
4. In **Google Search Console**, use URL Inspection → "Test live URL" on `/`, confirm the rendered HTML, then **Request indexing** to force a re-crawl. Check the Pages report for the root being classified as a soft 404 / "Crawled – currently not indexed".

> A lightweight regression guard would be valuable here: a smoke test asserting `Content-Type: text/html` for `GET /` with a browser `Accept` header (extend `scripts/smoke-prod.sh`). This class of bug is invisible to type-checking and easy to reship.

## 2. 🟠 P1 — The HTML homepage and its structured data never ship

This is the direct consequence of #1, called out separately because of what is being lost. `apps/web/public/index.html` contains the strongest homepage SEO in the codebase:

- `WebSite` JSON-LD with a `SearchAction` `potentialAction` (Sitelinks Search Box).
- A descriptive `<h1>` ("Every name rides a wave."), keyword-relevant kicker ("American baby name history & trends since 1880"), and a `<noscript>` fallback image.
- A full `<nav>` linking the eight primary hubs — the site's main internal-link distribution point.

None of this is currently delivered. Fixing #1 restores all of it; no separate work is required, but confirm the `SearchAction` validates in the [Rich Results Test](https://search.google.com/test/rich-results) once live.

## 3. ✅ What's already excellent (preserve these)

These were verified live and are genuinely strong — don't regress them:

- **Server-side rendering of name pages.** `/name/Emma/` ships ~736 words of unique, data-driven copy, a single `<h1>`, and full content in the initial HTML (no JS required to index). Not thin content.
- **Per-page metadata is dynamic and high quality.** Titles like `Emma name popularity (Stable Decline, peak 2003) | NobodyNamed` and descriptions that include peak year, counts, and trend — keyword-rich and unique per URL (`render-name.ts`, `[slug].ts`).
- **Structured data on every template:**
  - Name pages: `BreadcrumbList` + `WebPage` + `Dataset` (with `temporalCoverage`, `creator`, `variableMeasured`) — excellent and topically apt.
  - Editorial hubs: `BreadcrumbList` + `CollectionPage`.
  - Blog posts: `BlogPosting` + `BreadcrumbList` + `Person` author.
- **Canonicalization is rigorous.** `http→https` (301), `www→apex` (301), trailing-slash enforcement (`/name/Emma` → `/name/Emma/`, `/extinct/` → `/extinct`), `/comebacks → /comeback`, and `/era/{year} → /year/{year}/` are all handled in `_middleware.ts` / `_redirects`. Every page carries a self-referential `<link rel="canonical">`.
- **Correct HTTP semantics.** Unknown names and paths return real `404`s (no soft-404 200s); legacy `?name=` URLs 301 to clean paths.
- **Dynamic OG images.** `/api/og/Emma` and `/api/og/default` both return `200 image/png` — per-name social cards with `og:image:alt` and `twitter:card=summary_large_image`.
- **Edge performance.** TTFB ~70–80 ms, name page ~35 KB, year page ~9 KB, all behind Cloudflare with sensible `s-maxage` + `stale-while-revalidate`. Core Web Vitals should be easy wins here.
- **robots.txt** is clean: `Allow: /`, sitemap declared, plus a forward-looking `Content-Signal` directive. No accidental `noindex`/`Disallow` on indexable pages anywhere checked.
- **Strong internal linking from name pages** (`renderExploreLinks`): status hubs, peak-year, decade, first-letter, last-letter, "twin", and "shadow" links create a dense, crawlable graph — *once the homepage starts feeding it again.*

## 4. 🟡 P2 — Smaller fixes

### 4.1 Homepage OG image type mismatch
`public/index.html` declares:
```html
<meta property="og:image" content="https://nobodynamed.com/api/og/default">
<meta property="og:image:type" content="image/svg+xml">
```
But `/api/og/default` actually returns `image/png`. The declared type is wrong. Some scrapers reject mismatched types or fail to render the preview. **Fix:** set `og:image:type` to `image/png` (matching the live endpoint and the name-page templates, which already declare `image/png` correctly).

### 4.2 XML sitemap: no `<lastmod>`, limited name coverage
`sitemap.xml.ts` emits `<url><loc>…</loc></url>` with no `<lastmod>`, `<changefreq>`, or `<priority>`. Since the dataset only changes ~once/year (SSA release) and you already track a `data_version` UUID in `meta`:

- Add `<lastmod>` (e.g. derived from the SSA release date / `data_version` timestamp) so crawlers can cheaply detect that the vast majority of pages are unchanged between annual updates — this improves crawl efficiency on a large site.
- The sitemap currently lists ~2k URLs (static hubs + years + decades + letters + a curated `listIndexableNames` slice) against ~100k name/sex records. That curation is reasonable, but see §6 for expanding it.

## 5. 🟢 P3 — Polish

- **OG image dimensions.** Add `og:image:width` / `og:image:height` (and `twitter:image` is already set) so Facebook/LinkedIn/Slack render the large card immediately without a fetch round-trip. The generator presumably emits a fixed size (e.g. 1200×630) — declare it.
- **Sitewide `Organization` schema.** Consider an `Organization` (or `WebSite` with `publisher`) node so the brand entity is unambiguous; pair with a logo for Knowledge Panel eligibility. The homepage `WebSite` node (once served) is a good anchor for this.
- **Blog `Article` images.** Confirm `BlogPosting` entries include an `image` property (required for article rich results); the schema currently shows `BlogPosting`/`Person`/`datePublished` but image was not verified.
- **`<meta name="author">` / dates on blog** are nice-to-haves for E-E-A-T signals on the editorial content.

## 6. 📈 Growth opportunities

These are not defects — they're upside, given how solid the foundation is.

1. **Expand indexable name coverage.** ~100k name/sex pages exist but only a curated subset is in the sitemap. Many long-tail `[name]` queries ("is the name ___ popular", "___ name meaning popularity") are low-competition. Consider widening `listIndexableNames` to every name with enough historical signal to render non-trivial content, and moving to a **sitemap index** (`/sitemap.xml` → child sitemaps of ≤50k URLs each) to stay within limits as coverage grows. Gate on content quality so you don't index near-empty pages (thin-content risk).
2. **Lean into the editorial hubs.** `/millennial-names`, `/gen-z-names`, `/classic-names`, `/comeback`, `/future-grandparent-names` target high-volume head terms. Each is currently a short lede + a handful of cards. Adding 300–500 words of genuinely useful copy and more internal links per hub would make them competitive for those terms.
3. **FAQ / Q&A content on name pages.** Name searchers ask predictable questions ("When was ___ most popular?", "Is ___ a boy or girl name?", "Is ___ still popular?"). The data to answer these is already on the page — surfacing it as a short Q&A block (optionally with `FAQPage` schema) maps directly onto People-Also-Ask and AI-overview surfaces.
4. **Verify GSC coverage post-fix.** Once #1 ships, watch Search Console for: homepage indexing recovery, impressions on brand/navigational queries, and any "Crawled – currently not indexed" buildup on name pages that signals quality thresholds.

## 7. What this audit could *not* cover

The connected Ahrefs API plan returned `Insufficient plan` for Site Explorer, Site Audit, Rank Tracker, and GSC endpoints, so the following were **not** assessed and should be a follow-up:

- Backlink profile, referring domains, and Domain Rating.
- Organic keyword rankings, traffic estimates, and ranking trends.
- Competitor gap analysis (vs. behindthename, babynames.com, nameberry, SSA itself).
- Real-world Core Web Vitals field data (CrUX) and a full Lighthouse pass.
- Crawl-level issue detection across the full URL set (broken links, redirect chains, orphan pages).

Recommend connecting Google Search Console + a crawl tool (or an Ahrefs plan with Site Audit) for a follow-up pass focused on off-page and field-performance data.

## Priorities recap

1. **Ship the homepage HTML fix (#1/#2) today.** Everything else is secondary — the root currently has no HTML SEO at all.
2. Add a `Content-Type: text/html` smoke test for `GET /` so it can't silently regress again.
3. Fix the OG image type mismatch (#4.1) and add sitemap `<lastmod>` (#4.2) in the same release.
4. Then pursue coverage expansion and editorial depth (§6) as ongoing growth work.
